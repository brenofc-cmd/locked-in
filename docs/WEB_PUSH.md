# Web Push (V2 Phase 10)

Notifications that arrive with LOCKED IN closed — opt-in per device, a few useful kinds, once each,
never in quiet hours, never with private content. ADR-092…099. No hype, just proof.

## Architecture

```
pg_cron (every minute)
  └─ private.push_tick()                         SQL, idempotent
       ├─ private.push_enqueue(now())            due reminders → notification_deliveries
       │                                         (unique user + dedup key; outside quiet hours)
       ├─ delete deliveries older than 30 days
       └─ only if something is pending:
            net.http_post(vault push_dispatch_url,
                          header x-li-dispatch = vault push_dispatch_secret)
                 │
                 ▼
Edge Function push-dispatch (Deno, verify_jwt off, own secret check)
  ├─ VAPID keys from Vault (generated here once; the private key never leaves)
  ├─ private.push_claim(25)        SKIP LOCKED batch → sending
  ├─ for each device: RFC 8291 encryption + RFC 8292 VAPID (WebCrypto) → POST to the push service
  └─ private.push_finish(id, statuses)   2xx sent · 404/410 device deleted · 429/5xx/network retried
                 │
                 ▼
Browser push service (FCM / Mozilla / Apple / WNS) → the device
  └─ public/sw.js: push → notification (title, body, route KEY) · click → whitelisted route
```

One scheduler (Supabase `pg_cron`), one sender (the Edge Function), one service worker. No Vercel
Cron (the Hobby plan runs a cron at most once a day) and no service-role key in Vercel: the Edge
Function reaches the database with the platform's own `SUPABASE_DB_URL`.

Code: `supabase/migrations/20261006105842_web_push.sql`, `supabase/functions/push-dispatch/`
(`index.ts` entry, `webpush.ts` crypto, `message.ts` text, `routes.ts` shared with the app),
`public/sw.js`, `src/lib/push.ts`, `src/components/push/`, `src/app/(app)/push-actions.ts`,
`src/app/offline/route.ts`, Settings → Notificações push.

## VAPID and secrets

| Value                   | Where                                                          | Who sets it                                                    |
| ----------------------- | -------------------------------------------------------------- | -------------------------------------------------------------- |
| VAPID private key (JWK) | Supabase Vault `push_vapid_private_jwk`                        | Generated by `push-dispatch` on its first call                 |
| VAPID public key        | Vault `push_vapid_public_key` → `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | Read once with SQL, set in Vercel / `.env.local` (public)      |
| VAPID subject           | `https://locked-in-rust.vercel.app` (in the function)          | Code (no e-mail is exposed)                                    |
| Dispatch secret         | Vault `push_dispatch_secret`                                   | Generated inside the database (`gen_random_bytes`)             |
| Dispatch URL            | Vault `push_dispatch_url`                                      | `https://<project-ref>.supabase.co/functions/v1/push-dispatch` |

Nobody types, copies or sees a private value. Never put a private key in the repo, the client, logs,
docs or browser storage.

**Environments.** Each Supabase project has its own Vault and keys.

- DEV (`oavhuxaanztrughyrckb`): `.env.local` and Vercel **Preview** / **Development** use the DEV
  public key.
- PROD (`xhjczzhmbulaiebpsktl`): Vercel **Production** uses the PROD public key.

A subscription is bound to the key it was created with; `syncPushDevice()` drops a subscription made
with another key, so changing keys is safe (devices re-enable).

## Setup of an environment (once)

1. Apply the migration (pg_cron, pg_net, tables, functions, the `locked-in-push-tick` job).
2. Deploy `push-dispatch` with `verify_jwt = false` (it checks its own secret).
3. In SQL (values generated in place, never shown):

   ```sql
   select vault.create_secret('https://<ref>.supabase.co/functions/v1/push-dispatch', 'push_dispatch_url');
   select vault.create_secret(encode(extensions.gen_random_bytes(32), 'hex'), 'push_dispatch_secret');
   -- wake the function once: it creates the VAPID pair
   select net.http_post((select decrypted_secret from vault.decrypted_secrets where name = 'push_dispatch_url'),
     '{}'::jsonb, '{}'::jsonb,
     jsonb_build_object('Content-Type', 'application/json', 'x-li-dispatch',
       (select decrypted_secret from vault.decrypted_secrets where name = 'push_dispatch_secret')));
   select decrypted_secret from vault.decrypted_secrets where name = 'push_vapid_public_key'; -- public
   ```

4. Set `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (that public key) for the matching Vercel environment and
   redeploy (it is inlined at build time).

## Service worker (`public/sw.js`)

- The only worker, scope `/`, registered on every page after load (never asks for anything).
- `push`: reads `{k, t, b, r, g}`; title ≤ 80, body ≤ 160 characters; `r` is a route **key** looked up
  in `ROUTES` (same table as `routes.ts`, a unit test keeps them equal) — a URL is never taken from a
  payload; unknown → `/today`. A focused LOCKED IN window already shows things in the app, so the
  notification is skipped then (except a test notification).
- `notificationclick`: focus an open LOCKED IN window and navigate it, else `openWindow(route)`. The
  route is explicit, so Resume State (which acts only at `/`) never overrides it.
- `fetch`: page navigations only, network first (navigation preload); when the network fails the
  static `/offline` page is shown. Nothing else is intercepted or cached: no page, no API / Supabase
  / auth response, no token. Cache: `locked-in-offline-v1` with one entry.
- Updates: `skipWaiting` + `clients.claim`, `/sw.js` served with `Cache-Control: no-store`; there is
  no cached app shell that could go stale.

## Subscription lifecycle

- **Enable** (Configurações → "Ativar neste dispositivo"): the only place `Notification.requestPermission()`
  runs. Granted → `pushManager.subscribe` (userVisibleOnly, the VAPID key) → `savePushSubscription`
  upserts `{endpoint, p256dh, auth, user_agent label}`.
- **Multi-device**: one row per browser / device; a user may have several. Everything is sent to
  every device of the user.
- **Disable here**: the row is deleted, then the browser unsubscribes.
- **States** (always in text): Ativas neste dispositivo · Desativadas · bloqueadas (denied, never
  re-prompted) · não suportado · iPhone: instale na Tela de Início · indisponível neste ambiente.
- **Opt-in only**: no device is ever enabled silently; the kind switches (Planner, Toques, Reviews,
  Planejamento semanal, Ocultar detalhes) only matter for enabled devices.

## Sign-out and shared devices

- **Sair** sends this device's endpoint with the sign-out form; `/auth/signout` deletes that row in
  the same request (RLS: only the caller's own) and the browser unsubscribes.
- **On every open** (signed in) `syncPushDevice()` asks whether the browser's subscription is the
  signed-in user's; if not (a session that ended without Sair, someone else's account), it is
  unsubscribed at once — the previous user's row then dies at the push service (404 / 410).
- **Taking over** an endpoint that is still another user's row is refused by RLS (`42501`); the
  client drops it and subscribes afresh.
- Result: B never receives A's pushes on a shared browser (e2e test 5; pgTAP "cannot be taken over").

## What is pushed

| Kind                 | When (owner's timezone)                                                                                         | Opens        | Expires                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------ |
| Planner              | 08:00 of `event_date − reminder_days_before` (0 / 1 / 3 / 7); on the day of a timed event at most 2 h before it | `/planner`   | event start (untimed: its day) |
| DAR UM TOQUE         | the nudge (Phase 6 limits unchanged; delivery only)                                                             | `/partner`   | end of the recipient's day     |
| Review do dia        | 21:00, a day with tasks and no reflection                                                                       | `/today`     | end of the day                 |
| Review semanal       | Sunday 19:00, a week with tasks and no reflection                                                               | `/progress`  | end of Sunday                  |
| Planejamento semanal | Monday 08:00, a week without priorities                                                                         | `/plan/week` | end of Monday                  |
| Teste                | ENVIAR NOTIFICAÇÃO DE TESTE (≤ 1 a minute), ignores quiet hours                                                 | `/settings`  | 10 minutes                     |

Not pushed (in-app only): task completions, celebrations, commitments, reactions, partner activity.
A device with push on does not also get the in-app browser notification for a planner reminder.

## Quiet hours

The existing `user_settings` window (`[start, end)` local, wraps midnight, `start = end` = none —
`private.push_quiet` = `inQuietHours`). A due reminder is not created while quiet; it is created when
the window ends **if it is still before its expiry and less than 24 h late**. So "Prova amanhã" never
arrives after the exam started, and a reminder is never sent days late.

## Dedup, retries, cleanup

- `notification_deliveries unique (user_id, dedup_key)`: `planner:<event>:<n>:<date>`,
  `nudge:<id>`, `review-day:<date>`, `review-week:<monday>`, `plan-week:<monday>`, `test:<second>`.
  The scheduler can run any number of times (at-least-once) — one delivery per logical event.
- Claim: `FOR UPDATE SKIP LOCKED` (two runs never take the same row); a run that died releases its
  rows after 5 minutes; an expired row becomes `expired`, never sent.
- Outcome per device: 2xx → `sent` (`last_success_at`); 404 / 410 → the device is deleted; 429 / 5xx /
  network → `pending` again with backoff 2, 4, 8, 16 min, `failed` after 5 attempts; other 4xx →
  `rejected`; a device failing 10 times in a row is deleted. A delivery whose source is gone (event
  deleted) is `skipped`.
- Retention: deliveries older than 30 days are deleted by the tick.
- Partial success: once any device accepted, the delivery is `sent` (failed devices are not retried).

## Privacy

- Owner-only tables; partner, outsider and anon read nothing (pgTAP `v2_phase10_push`).
- No payload is stored; the text is built at send time from: planner title / type / days / time,
  the nudging partner's name and the commitment title. Never a goal, vision, mirror, reflection,
  non-negotiable, private task or anything of the partner beyond the nudge.
- **Ocultar detalhes**: "Lembrete do Planner" / "Você recebeu um toque", no titles.
- The payload is encrypted end to end (aes128gcm); the push service sees only the endpoint.
- Logs: the function logs counts only (`push-dispatch: {"claimed":1,"sent":1,…}`); never an endpoint,
  key, payload or user id.

## Troubleshooting

| Symptom                                    | Check                                                                                       |
| ------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Settings says "indisponível"               | `NEXT_PUBLIC_VAPID_PUBLIC_KEY` missing in that build                                        |
| Nothing is sent                            | `cron.job` has `locked-in-push-tick` active; Vault has `push_dispatch_url` / `_secret`      |
| Function answers 401                       | the secret in the request ≠ Vault (`net._http_response`)                                    |
| Deliveries stay `pending` with `transient` | push service down / 429; they retry with backoff                                            |
| Device disappears                          | the push service answered 404 / 410 (unsubscribed / expired) — re-enable on the device      |
| Chrome "updated in the background"         | a push arrived while no notification was shown — the worker always shows one unless focused |
| iPhone shows "instale na Tela de Início"   | open LOCKED IN from the Home Screen (iOS 16.4+), then enable                                |
